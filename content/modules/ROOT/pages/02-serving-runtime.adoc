= Build a vLLM Serving Runtime
:navtitle: 2. Build a vLLM Serving Runtime

_Estimated time: 15 minutes_

In this module you will:

* Understand why KServe separates runtime definitions from model deployments
* Create a ServingRuntime that configures vLLM for CPU inference
* Verify the runtime is registered and ready for use

A KServe *ServingRuntime* defines *how* to run models -- the container image, startup flags, and resource constraints.
It does not deploy a model. Think of it as a template: "when someone asks to serve a vLLM model, use this container with these arguments."

In this module you will create the ServingRuntime from scratch and understand every field.

== Why Separate the Runtime from the Model?

In a traditional deployment, you bake everything together: the model server binary, its configuration, the model weights, and the resource limits all go into one Deployment YAML. That works for one model, but it does not scale.

KServe introduces a separation of concerns. The *ServingRuntime* defines the _how_: which container image runs the inference server, what flags it starts with, and how much CPU and memory it needs. The *InferenceService* (Module 3) defines the _what_: which model to load and where to find its weights.

This separation means you can:

* Update the vLLM version across all models by editing one ServingRuntime
* Deploy five different models without duplicating server configuration
* Enforce resource policies (CPU limits, memory caps) in one place

For the HR assistant you are building, this means the same `vllm-cpu` runtime could serve TinyLlama today and a larger model tomorrow -- without changing any deployment configuration.

== Create the Project

First, create a dedicated OpenShift project for your CPU inference stack:

[source,bash,role="execute",subs="attributes+"]
----
oc new-project {project_name}
----

Verify you are in the correct project:

[source,bash,role="execute",subs="attributes+"]
----
oc project
----

== Understand the ServingRuntime

Before you apply anything, read through the YAML below. Every field is explained.

[source,yaml]
----
apiVersion: serving.kserve.io/v1alpha1
kind: ServingRuntime
metadata:
  name: vllm-cpu                                    # <1>
  annotations:
    openshift.io/display-name: vLLM CPU ServingRuntime
spec:
  annotations:
    prometheus.io/port: "8080"
    prometheus.io/path: /metrics
  multiModel: false                                  # <2>
  supportedModelFormats:
    - autoSelect: true
      name: vLLM                                     # <3>
  containers:
    - name: kserve-container
      image: registry.redhat.io/rhaii/vllm-cpu-rhel9:latest  # <4>
      command:
        - python
        - -m
        - vllm.entrypoints.openai.api_server
      args:
        - "--port=8080"
        - "--model=/mnt/models"
        - "--dtype=bfloat16"                         # <5>
        - "--enable-auto-tool-choice"                # <6>
        - "--tool-call-parser=hermes"
        - "--max-model-len=2048"                     # <7>
      ports:
        - containerPort: 8080
          protocol: TCP
      resources:                                     # <8>
        requests:
          cpu: "8"
          memory: 8Gi
        limits:
          cpu: "12"
          memory: 12Gi
----

<1> *name* -- other resources reference this name when they want to use this runtime.
<2> *multiModel: false* -- each pod serves exactly one model. This simplifies resource planning.
<3> *supportedModelFormats* -- declares that this runtime handles the "vLLM" format. The InferenceService you create in Module 3 will match on this name.
<4> *image* -- the Red Hat certified vLLM image built for CPU. This image includes Intel-optimized PyTorch and oneDNN backends that target AMX/AVX-512 automatically.
<5> *--dtype=bfloat16* -- selects the AMX hardware path on supported {intel_platform} processors. On older CPUs without AMX, vLLM falls back to AVX-512 BF16 emulation.
<6> *--enable-auto-tool-choice / --tool-call-parser=hermes* -- enables OpenAI-compatible function calling. The model can invoke tools defined in the API request.
<7> *--max-model-len=2048* -- caps the context window at 2048 tokens. Larger windows consume more memory and slow inference. For a RAG use case with short document chunks, 2048 is sufficient.
<8> *resources* -- CPU inference needs adequate cores. 8 cores requested, 12 limit. Memory must hold the model weights (~2.2 GB for TinyLlama BF16) plus KV cache.

== Create the ServingRuntime

Apply the resource to your project:

[source,bash,role="execute",subs="attributes+"]
----
cat <<'EOF' | oc apply -n {project_name} -f -
apiVersion: serving.kserve.io/v1alpha1
kind: ServingRuntime
metadata:
  name: vllm-cpu
  annotations:
    openshift.io/display-name: vLLM CPU ServingRuntime
spec:
  annotations:
    prometheus.io/port: "8080"
    prometheus.io/path: /metrics
  multiModel: false
  supportedModelFormats:
    - autoSelect: true
      name: vLLM
  containers:
    - name: kserve-container
      image: registry.redhat.io/rhaii/vllm-cpu-rhel9:latest
      command:
        - python
        - -m
        - vllm.entrypoints.openai.api_server
      args:
        - "--port=8080"
        - "--model=/mnt/models"
        - "--dtype=bfloat16"
        - "--enable-auto-tool-choice"
        - "--tool-call-parser=hermes"
        - "--max-model-len=2048"
      ports:
        - containerPort: 8080
          protocol: TCP
      resources:
        requests:
          cpu: "8"
          memory: 8Gi
        limits:
          cpu: "12"
          memory: 12Gi
EOF
----

=== Verify

Confirm the ServingRuntime was created:

[source,bash,role="execute",subs="attributes+"]
----
oc get servingruntime -n {project_name}
----

You should see output like:

----
NAME       DISABLED   MODELTYPE   CONTAINERS          AGE
vllm-cpu              vLLM        kserve-container    10s
----

Inspect the details to confirm your flags are set correctly:

[source,bash,role="execute",subs="attributes+"]
----
oc describe servingruntime vllm-cpu -n {project_name} | grep -A 5 "Args:"
----

Expected output includes `--dtype=bfloat16`, `--enable-auto-tool-choice`, and `--max-model-len=2048`. If any flag is missing, delete the runtime (`oc delete servingruntime vllm-cpu`) and re-apply the YAML.

=== Troubleshooting

[cols="1,2",options="header"]
|===
|Symptom |Resolution

|`oc new-project` returns "already exists"
|The project was created in a previous attempt. Run `oc project {project_name}` to switch to it.

|`oc get servingruntime` returns "No resources found"
|The apply command may have failed silently. Re-run the `oc apply` command and check for YAML indentation errors.

|ServingRuntime shows but InferenceService fails later
|Check that `supportedModelFormats.name` is exactly `vLLM` (case-sensitive). The InferenceService matches on this string.
|===

== What This Does Not Do

The ServingRuntime is a *definition*, not a deployment. No pods are running yet. No model has been loaded.
KServe separates the *how* (ServingRuntime) from the *what* (InferenceService) deliberately -- one runtime serves many models, and changing the image or flags updates all deployments that use it.
