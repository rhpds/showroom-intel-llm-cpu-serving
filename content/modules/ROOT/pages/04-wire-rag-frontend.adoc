= Wire a RAG Frontend
:navtitle: 4. Wire a RAG Frontend

_Estimated time: 15 minutes_

In this module you will:

* Understand why a RAG workbench is separate from the model server
* Deploy AnythingLLM and connect it to the vLLM endpoint
* Verify end-to-end connectivity from the chat UI to CPU inference

You have a model endpoint. Now you need a frontend that connects to it, adds document retrieval, and gives users a chat interface.
In this module you will deploy AnythingLLM and wire it to the vLLM endpoint you created in Module 3.

== Know: Why Separate the Chat Layer from the Model?

Your vLLM endpoint from Module 3 is a raw API: send JSON, get JSON back. No chat history, no document retrieval, no user interface. That is by design — the model server should do one thing well.

A *RAG workbench* adds the layers that make the model useful to end users:

* *Chat interface* — a browser-based UI for conversational interaction
* *Document management* — upload, chunk, and embed documents
* *Vector storage* — store and search document embeddings
* *Retrieval pipeline* — find relevant documents before generating a response
* *Conversation memory* — maintain context across multiple messages

Separating these concerns means you can swap the model without touching the frontend, or replace the vector store without redeploying the model. For the HR assistant, this means you could upgrade from TinyLlama to a larger model later — AnythingLLM would not need to change.

== What Is AnythingLLM?

AnythingLLM is an open-source RAG workbench. It does not run the model — it connects to any OpenAI-compatible endpoint and adds document chunking, embedding, vector storage (LanceDB), RAG retrieval, and a chat UI.

In this lab, it serves three roles:

. *LLM Client* — sends chat completion requests to vLLM over the OpenAI API
. *Embedding Engine* — runs its own lightweight embedding model to vectorize documents (independent of vLLM)
. *Vector Store* — stores document embeddings in LanceDB, an embedded vector database that requires no external infrastructure

The key point: AnythingLLM is a *client* of the vLLM endpoint, not a model server. All inference happens on the {intel_platform} CPU via vLLM.

== Create the Configuration Secret

AnythingLLM reads its configuration from environment variables. You will create a Kubernetes Secret that tells it where to find the model.

Examine each field:

[source,yaml]
----
LLM_PROVIDER: localai                              # <1>
LOCAL_AI_BASE_PATH: http://tinyllama-1b-cpu-predictor:8080/v1  # <2>
LOCAL_AI_MODEL_PREF: TinyLlama/TinyLlama-1.1B-Chat-v1.0      # <3>
LOCAL_AI_MODEL_TOKEN_LIMIT: "512"                  # <4>
EMBEDDING_ENGINE: native                           # <5>
VECTOR_DB: lancedb                                 # <6>
----

<1> *LLM_PROVIDER* -- tells AnythingLLM to use the "LocalAI" provider, which speaks the OpenAI-compatible protocol.
<2> *LOCAL_AI_BASE_PATH* -- the internal KServe service URL. This is the Kubernetes service created by the InferenceService, reachable inside the cluster without a Route.
<3> *LOCAL_AI_MODEL_PREF* -- the model name as reported by `/v1/models`.
<4> *LOCAL_AI_MODEL_TOKEN_LIMIT* -- maximum tokens per response. Kept low because TinyLlama 1.1B has a 2048 token context and you need room for RAG context.
<5> *EMBEDDING_ENGINE: native* -- AnythingLLM runs its own embedding model for document vectorization, independent of vLLM.
<6> *VECTOR_DB: lancedb* -- uses the built-in LanceDB vector store. No external database needed.

Create the Secret:

[source,bash,role="execute",subs="attributes+"]
----
cat <<'EOF' | oc apply -n {project_name} -f -
apiVersion: v1
kind: Secret
metadata:
  name: anythingllm-config
type: Opaque
stringData:
  LLM_PROVIDER: localai
  LOCAL_AI_BASE_PATH: "http://tinyllama-1b-cpu-predictor:8080/v1"
  LOCAL_AI_MODEL_PREF: "TinyLlama/TinyLlama-1.1B-Chat-v1.0"
  LOCAL_AI_MODEL_TOKEN_LIMIT: "512"
  EMBEDDING_ENGINE: native
  VECTOR_DB: lancedb
EOF
----

== Deploy AnythingLLM

Create the Deployment that runs the AnythingLLM workbench:

[source,bash,role="execute",subs="attributes+"]
----
cat <<'EOF' | oc apply -n {project_name} -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: anythingllm
spec:
  replicas: 1
  selector:
    matchLabels:
      app: anythingllm
  template:
    metadata:
      labels:
        app: anythingllm
    spec:
      containers:
        - name: anythingllm
          image: ghcr.io/mintplex-labs/anything-llm:latest
          ports:
            - containerPort: 3001
          envFrom:
            - secretRef:
                name: anythingllm-config
          resources:
            requests:
              cpu: "1"
              memory: 1Gi
            limits:
              cpu: "2"
              memory: 2Gi
EOF
----

== Create the Service and Route

Expose AnythingLLM so you can access it from your browser:

[source,bash,role="execute",subs="attributes+"]
----
oc expose deployment anythingllm --port=3001 -n {project_name}
oc create route edge anythingllm --service=anythingllm --port=3001 -n {project_name}
----

== Wait for the Pod

[source,bash,role="execute",subs="attributes+"]
----
oc rollout status deployment/anythingllm -n {project_name} --timeout=120s
----

=== Verify: Pod is Running

[source,bash,role="execute",subs="attributes+"]
----
oc get pods -n {project_name} -l app=anythingllm
----

Expected output:

----
NAME                           READY   STATUS    RESTARTS   AGE
anythingllm-xxxxx-xxxxx        1/1     Running   0          30s
----

If the pod is not running, check events: `oc describe deployment anythingllm -n {project_name}`.

== Verify the Connection

Get the AnythingLLM URL:

[source,bash,role="execute",subs="attributes+"]
----
export ANYTHINGLLM_URL=$(oc get route anythingllm -n {project_name} -o jsonpath='https://\{.spec.host\}')
echo "AnythingLLM URL: $\{ANYTHINGLLM_URL\}"
----

Open that URL in your browser. Complete the initial setup wizard -- select the existing LLM configuration (it will auto-detect the settings from the Secret).

== Test the Wiring

Once setup is complete, create a workspace called *HR Assistant* and send a basic prompt:

----
What is the role of an HR representative?
----

The response flows through this path:

. You type a question in AnythingLLM
. AnythingLLM sends it as a chat completion to `http://tinyllama-1b-cpu-predictor:8080/v1`
. vLLM runs inference on {intel_platform} CPU
. The response returns to AnythingLLM and displays in the chat

This confirms end-to-end wiring. The model is answering from its training data only -- no documents are loaded yet. That comes in Module 5.

=== Verify: End-to-End Wiring

You should see a response from the model in the AnythingLLM chat interface. The response will be a general answer based on the model's training data — it will not reference any specific HR documents yet.

If you see an error like "Could not connect to LLM provider":

. Check that the vLLM pod is still running: `oc get pods -n {project_name}`
. Verify the service name: `oc get svc -n {project_name} | grep tinyllama`
. Check the secret values: `oc get secret anythingllm-config -n {project_name} -o yaml`

The internal URL `http://tinyllama-1b-cpu-predictor:8080/v1` must match the service name created by KServe in Module 3.

=== Troubleshooting

[cols="1,2",options="header"]
|===
|Symptom |Resolution

|AnythingLLM UI shows "Could not connect to LLM provider"
|The vLLM service name in the secret may be wrong. Verify with `oc get svc -n {project_name}` and check that `LOCAL_AI_BASE_PATH` matches.

|AnythingLLM pod in `CrashLoopBackOff`
|Check logs: `oc logs -l app=anythingllm -n {project_name}`. Common cause: the secret is missing or malformed.

|Chat returns empty responses
|The model may still be loading. Check vLLM pod status: `oc get pods -n {project_name}`. Also verify `LOCAL_AI_MODEL_PREF` matches the exact model name from `/v1/models`.

|Route returns 503
|The AnythingLLM pod may not be ready. Wait for the rollout to complete and retry.
|===
