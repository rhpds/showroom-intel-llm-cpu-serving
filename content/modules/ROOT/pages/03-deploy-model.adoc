= Deploy a Model on CPU
:navtitle: 3. Deploy a Model on CPU

_Estimated time: 15 minutes_

In this module you will:

* Learn how the ModelCar pattern packages model weights as OCI images
* Deploy TinyLlama 1.1B as a KServe InferenceService on CPU
* Test the model endpoint with the OpenAI-compatible API

You have a ServingRuntime that defines *how* to run vLLM on CPU.
Now you will create an InferenceService that deploys TinyLlama 1.1B and makes it available as an OpenAI-compatible API endpoint.

== Know: How Models Get to the Pod

Deploying an LLM requires getting model weights (often gigabytes of files) into a running container. There are three common patterns:

[cols="1,2,2",options="header"]
|===
|Pattern |How It Works |Trade-offs

|*HuggingFace Download*
|Pod downloads weights from HuggingFace Hub on startup
|Simple, but slow startup (minutes), requires internet access, not reproducible (model can change upstream)

|*PVC Mount*
|Weights stored on a PersistentVolumeClaim, mounted into the pod
|Fast startup if pre-loaded, but requires storage provisioning and manual management

|*ModelCar (OCI Image)*
|Weights packaged as a container image, pulled like any other image
|Fast restart (node-level caching), reproducible (pinned by digest), air-gap compatible
|===

This lab uses the *ModelCar* pattern. The TinyLlama 1.1B weights are pre-packaged at `oci://quay.io/rh-aiservices-bu/tinyllama:1.0`. When KServe creates the pod, it pulls this image in an init container, extracting the weights into `/mnt/models` before vLLM starts.

The key benefit for production: when a pod restarts or scales, the node already has the image cached. Startup drops from minutes to seconds.

== Understand the InferenceService

Read through the YAML before applying it:

[source,yaml]
----
apiVersion: serving.kserve.io/v1alpha1
kind: InferenceService
metadata:
  name: tinyllama-1b-cpu                                # <1>
  annotations:
    serving.kserve.io/deploymentMode: RawDeployment      # <2>
spec:
  predictor:
    model:
      modelFormat:
        name: vLLM                                       # <3>
      runtime: vllm-cpu                                  # <4>
      storageUri: oci://quay.io/rh-aiservices-bu/tinyllama:1.0  # <5>
----

<1> *name* -- becomes the Kubernetes service name. Other components will connect to `tinyllama-1b-cpu-predictor` on port 8080.
<2> *RawDeployment* -- deploys as a standard Kubernetes Deployment rather than a Knative service. Simpler networking, no scale-to-zero complexity.
<3> *modelFormat.name: vLLM* -- matches the `supportedModelFormats` entry in the ServingRuntime you created in Module 2.
<4> *runtime: vllm-cpu* -- explicitly selects your ServingRuntime by name.
<5> *storageUri* -- the OCI image containing TinyLlama 1.1B weights. The `oci://` prefix tells KServe to pull this as a container image.

Notice what is *absent*: no GPU tolerations, no `nvidia.com/gpu` resource requests. This InferenceService runs entirely on CPU.

== Create the InferenceService

[source,bash,role="execute",subs="attributes+"]
----
cat <<'EOF' | oc apply -n {project_name} -f -
apiVersion: serving.kserve.io/v1alpha1
kind: InferenceService
metadata:
  name: tinyllama-1b-cpu
  annotations:
    serving.kserve.io/deploymentMode: RawDeployment
spec:
  predictor:
    model:
      modelFormat:
        name: vLLM
      runtime: vllm-cpu
      storageUri: oci://quay.io/rh-aiservices-bu/tinyllama:1.0
EOF
----

== Watch the Pod Start

Monitor the pod as it pulls the model weights and starts vLLM:

[source,bash,role="execute",subs="attributes+"]
----
oc get pods -n {project_name} -w
----

Press `Ctrl+C` once you see the predictor pod reach `Running` status. The startup sequence:

. *Init container* pulls the ModelCar image (~2.2 GB of model weights)
. *vLLM container* starts, loads the weights into memory, and initializes the CPU inference engine
. The pod reports `Ready` when the model is loaded and the health endpoint responds

[NOTE]
====
The first startup takes 3-5 minutes because the ModelCar image must be pulled from the registry. Subsequent restarts are faster due to node-level image caching.
====

=== Verify: Pod is Running

[source,bash,role="execute",subs="attributes+"]
----
oc get pods -n {project_name} -l serving.kserve.io/inferenceservice=tinyllama-1b-cpu
----

Expected output:

----
NAME                                          READY   STATUS    RESTARTS   AGE
tinyllama-1b-cpu-predictor-xxxxx-xxxxx        1/1     Running   0          3m
----

If the pod is stuck in `Init:0/1`, the ModelCar image is still downloading. Wait 3-5 minutes on first pull.

== Verify the InferenceService

Check that the InferenceService reports `READY = True`:

[source,bash,role="execute",subs="attributes+"]
----
oc get inferenceservice -n {project_name}
----

Expected output:

----
NAME               URL                                                   READY   AGE
tinyllama-1b-cpu   https://tinyllama-1b-cpu-predictor-yourns.apps...     True    5m
----

The `URL` column shows the external endpoint. The `READY` column must show `True` before proceeding.

If `READY` shows `False`, check the pod logs: `oc logs -l serving.kserve.io/inferenceservice=tinyllama-1b-cpu -n {project_name}`.

== Test the Model Endpoint

First, get the model endpoint URL:

[source,bash,role="execute",subs="attributes+"]
----
export VLLM_URL=$(oc get route tinyllama-1b-cpu-predictor -n {project_name} -o jsonpath='https://\{.spec.host\}')
echo "vLLM endpoint: $\{VLLM_URL\}"
----

List available models:

[source,bash,role="execute"]
----
VLLM_URL=$(oc get route tinyllama-1b-cpu-predictor -n $(oc project -q) -o jsonpath='https://{.spec.host}')
curl -s ${VLLM_URL}/v1/models | python3 -m json.tool
----

You should see `TinyLlama/TinyLlama-1.1B-Chat-v1.0` listed.

== Send a Chat Completion

Test the endpoint with a real prompt:

[source,bash,role="execute"]
----
VLLM_URL=$(oc get route tinyllama-1b-cpu-predictor -n $(oc project -q) -o jsonpath='https://{.spec.host}')
curl -s ${VLLM_URL}/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "TinyLlama/TinyLlama-1.1B-Chat-v1.0",
    "messages": [
      {"role": "user", "content": "What is the capital of France? Answer in one sentence."}
    ],
    "max_tokens": 50
  }' | python3 -m json.tool
----

Observe the response. The `usage` block shows token counts, and latency is a few seconds -- expected for CPU inference. You now have a working LLM endpoint on CPU, accessible via the standard OpenAI-compatible API.

=== Verify: End-to-End Inference

The response JSON should contain:

* A `choices` array with a `message.content` field containing the answer
* A `usage` block showing `prompt_tokens`, `completion_tokens`, and `total_tokens`
* A `model` field showing `TinyLlama/TinyLlama-1.1B-Chat-v1.0`

If you see a connection error, verify the route exists: `oc get route -n {project_name}`. If you see a 503, the model is still loading -- wait and retry.

=== Troubleshooting

[cols="1,2",options="header"]
|===
|Symptom |Resolution

|Pod stuck in `Init:0/1` for more than 10 minutes
|The ModelCar image pull may be slow or blocked. Check events: `oc describe pod -l serving.kserve.io/inferenceservice=tinyllama-1b-cpu -n {project_name}`

|Pod in `CrashLoopBackOff`
|vLLM could not load the model. Check logs: `oc logs -l serving.kserve.io/inferenceservice=tinyllama-1b-cpu`. Common cause: insufficient memory -- the pod needs at least 8Gi.

|`curl` returns `Connection refused`
|The route may not exist. Run `oc get route -n {project_name}` and verify `tinyllama-1b-cpu-predictor` is listed.

|Response is very slow (30+ seconds)
|First request after startup is always slower (cold KV cache). Subsequent requests should be 2-10 seconds.
|===
